# 实施计划

对应 [requirements.md](requirements.md) 与 [design.md](design.md)。下列任务在需求与方案确认前不开始。确认后按编号实施，完成一项再勾选一项。

- [ ] 1. 建立 crate 与前端工程
- 建立 Rust crate `duolinzao`（Axum、Tokio、SQLx）和 `web/` 下的 Vue3 + TypeScript + Vite 工程
- 增加 `config.example.toml`，启动时校验总管理、WebAuthn、截止钟点、三餐餐后时刻、均分阈值、样本量下限、本地加密密钥、餐品图片目录和单张大小上限；缺项则拒绝启动。大小上限不写死在仓库里
- 邮箱能力默认可以关闭。关闭时不要求 SMTP，也不强制邮箱验证；开启时才要求 SMTP，并提供 magic link
- 由配置文件创建总管理，不提供总管理的邀请码注册
- _需求: 需求 1、需求 2、需求 18

- [ ] 2. 建立迁移、Scoped RBAC 与审计底座
- 按设计写入账号、角色分配、食堂绑定、会话、新设备待确认请求、报餐、菜谱、评分、评语、隐藏偏好、通知、LLM 渠道、审计和可修改设置的迁移
- 权限码使用需求 2 的固定集合。`canteen` 与 `admin` 分配保存 `canteen_id` 列表，`super_admin` 范围为 `*`
- 标签只写入 `admin` 分配的来源说明。鉴权不把标签当引擎，也不使用 ACL、ABAC、ReBAC 作为主模型
- 审计记录操作者、当时使用的角色、食堂范围或 `*`，并拒绝记录密码、TOTP 密钥、会话令牌、邀请码原文、magic link、LLM key 和餐品图片字节
- 保证未满 6 个月的审计不可被清除
- _需求: 需求 2、需求 15、需求 18

- [ ] 3. 完成注册、邀请码与食堂绑定
- 实现字符串账号 + 一次性邀请码注册，账号唯一
- 仅持有 `user.invite` 的账号可发放邀请码
- 员工可绑定多个食堂；食堂管理人员与普通绑定分开存储
- _需求: 需求 2、需求 3、需求 7

- [ ] 4. 完成登录、可选邮箱与新设备页内确认
- 邮箱能力开启时按 Passkey / WebAuthn、TOTP、邮箱 magic link、密码的顺序提供登录，密码仅作兜底
- 总管理可在后台关闭 magic link 与邮箱验证。关闭后不出现邮箱登录，注册不要求验证邮箱
- 邮箱能力开启时，使用 magic link 前再绑定邮箱
- 新设备创建待确认请求。已登录设备在页面打开时，以及页面保持打开期间，用页内确认层允许或拒绝
- 确认层展示 User-Agent、IP，以及能解析出的设备或浏览器名称
- 允许后向新设备发会话，并允许接着绑定本机 Passkey。拒绝后不发会话，并结束该请求
- 旧设备当时未打开时请求保持待确认，之后打开页面仍然弹出。不接入系统推送，也不实现扫码授权
- 只有本账号的已登录设备可以处理该请求
- 同一账号的会话并行保留；提供查看设备、踢设备和解除 Passkey
- 食堂账号允许多账号、多 Passkey
- 在 Chrome 与 Edge 上验收登录、页内确认和踢设备
- _需求: 需求 4、需求 5、需求 6、需求 17

- [ ] 5. 完成班制、模板套用、自动报餐与覆盖
- 只实现「上二休四」和自定义排班；设置班制要求 `shift.self_write`。上二休四保存锚点日，并按工作 2 天、休息 4 天循环
- 新用户可以手动报餐（`meal.self_write` / `meal.self_read`）；选定班制或完成过报餐之前不自动报餐
- 休息日不自动报餐，仍允许手动报餐
- 预设保存为该用户的一份个人 DSL。轻度改某一餐，或在预览里把绿色报餐切换成橙色不报，都写回这份 DSL
- 每日报餐由个人 DSL 生成。一键套用到多天。后一次生成覆盖尚未锁定的同餐；已锁定的餐不改
- 同一用户、同一日期、同一餐次只保留一条报餐
- _需求: 需求 8、需求 9、需求 16

- [ ] 6. 完成北京时间截止与管理员改单
- 到配置的北京时间钟点时，一次性锁定次日早、中、晚
- 锁定后拒绝没有 `meal.admin_override` 或食堂范围不覆盖的改单
- 范围覆盖该餐的 `admin` 与全局 `super_admin` 可以在锁定后修改，并写审计（操作者、角色、范围）
- 代码与示例配置不写死具体钟点
- _需求: 需求 10

- [ ] 7. 完成按食堂维护的菜谱
- 菜谱列表和菜品表单。新建和编辑是同一页的两态，布局以编辑态为准。只有该食堂 `menu.read` 可看列表，只有 `menu.write` 可新建、编辑和停用
- 每条记录必须填写类别，且只能是菜、饭、汤之一。菜是热菜、凉菜等菜肴，饭是米饭、面食等主食，汤是汤。列表按这三类分组或筛选，不混成一张列表。缩略图可以显示，不强制；没有图片时用中性占位
- 新建菜和编辑菜可以上传、更换或移除一张 JPEG、PNG 或 WebP，并维护口味标签。库里存 `image_path`，接口给 `image_url`。不上传也能保存。超过配置大小上限或类型不符时拒绝。没有 `menu.write` 不能改图片或标签
- 员工绑定食堂不自动得到 `menu.write`
- 停用须在菜品表单的编辑态确认，不能从强提醒自动停用
- _需求: 需求 7、需求 11

- [ ] 8. 完成明线评分、评语与暗线偏好
- 只有 `rating.self_write` 可以打分；只接受已报过的餐，窗口为配置的餐后时刻起 7 日
- 分数只接受 −2、−1、0、1、2；无默认好评；只提交评语时拒绝
- 同一用户、日期、餐次、菜只保留一条评分，不提供改分和删除评语接口
- 评语最长 300 字，可选匿名。管理端查看评语要求覆盖该食堂的 `comment.admin_read`，查看评分要求 `rating.admin_read`；匿名时不返回账号
- 员工打分、评分汇总和评语都按菜、饭、汤分组或筛选，不混成一张列表
- 员工打分和评分汇总在餐品旁显示图片；没有图片时用中性占位。取图沿用评分权限，不新增权限码
- 员工端不展示菜品排行
- 每次成功打分后更新该用户对该菜的隐藏平均分；响应与界面不出现数值、倾向、权重、Elo
- _需求: 需求 14、需求 15

- [ ] 9. 完成选菜优化与强提醒
- 提供独立的选菜画面，仅对该食堂持有 `optimizer.read` 的账号开放，不新增权限码。默认是周视图：北京时间周一至周日，每天早、中、晚，每餐分列已选的菜、饭、汤
- 从周视图进入当餐选定。菜、饭、汤分成三组，在每一组内按该日该餐预计就餐人的隐藏偏好排序。偏好更高的更绿，更低的更红；无人评分用中性色。周视图和当餐选定都显示餐品图片和口味标签。标签不改变排序和色阶。不把三类排进同一列表
- 勾选和取消立即保存该食堂该日该餐的选定结果。离开或回到周视图后结果仍在。「保存并前进」按早餐、午餐、晚餐、下一天早餐跳转；周日晚餐跳到下周一早餐，用来把一周菜单定下来。这不是报餐截止锁
- 每一组内无人评分的靠后，颜色不标注数字，也不用装饰色代替偏好色阶
- 样本量达到下限且可见均分低于阈值时，向食堂人员写入站内强提醒。提醒列表按菜、饭、汤分组或筛选
- 强提醒不修改菜的启用状态
- 只有 `rating.strong_alert_config` 可在运行中修改均分阈值和样本量下限
- _需求: 需求 12、需求 13、需求 15、需求 17

- [ ] 10. 完成统一模板生成器
- 只暴露 `POST /api/meal-templates/generate`
- 总管理在「LLM 渠道配置」维护全站渠道，要 `system.super`，不新增权限码。员工端不提供 key 配置
- 按该列表保存的顺序尝试本地脚本与 LLM；前一条失败再用下一条
- 至少支持 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages
- DeepSeek、通义和其它兼容服务通过 base URL 与模型名配置
- key 加密保存，接口不回传 key 原文，服务端不内置供应商密钥
- 生成结果和之后的手改都写入该用户的同一份个人 DSL
- _需求: 需求 16

- [ ] 11. 完成站内提示与推送预留
- 一期提示写入站内通知，并提供读取接口
- `POST /api/push/reservations` 固定返回 `501 push_not_in_phase1`，不连接浏览器推送服务
- _需求: 需求 17

- [ ] 12. 完成导出、账号找回与镜像交付
- 持有 `export.run` 的总管理可导出食堂、菜谱、餐品图片、报餐、评分、评语和审计，排除密钥与密码哈希
- 持有 `user.recover` 的总管理可重置密码或清除失效登录材料，使账号恢复可登录
- 持有 `audit.read` 的总管理可查看含操作者、角色和范围的审计
- 构建包含前端产物与 Axum 二进制的 Docker 镜像；数据库由部署方单独运行。餐品图片放在挂载目录，不打进镜像
- 镜像与仓库保留 AGPL-3.0 许可证
- _需求: 需求 1、需求 18

- [ ] 13. 实现员工端竖屏主流程
- 按 `docs/ui/` 的员工参考图实现首页、班制、本周报餐、评分和模板预览。参考图不是像素级终稿。图和需求冲突时以需求为准
- 未选班制时首页标明默认不报餐，并提供选择班制和本周手动报餐
- 班制只列出「上二休四」和「自定义排班」。不实现参考图中的上五休二。描述生成进入模板生成器，不单列成班制
- 本周报餐按天显示早中晚、已绑定食堂切换、跨食堂提示和次日锁定提示
- 评分页对餐品提供 −2 到 2 和可选匿名评语（最多 300 字），并提示一周内可评。菜、饭、汤分开展示，不混成一张列表。参考图把不同类别排在一起，实现时仍然分开。评语挂在每一道餐品的评分上。餐品旁显示图片，没有图片时用中性占位
- 本周报餐之外另有「模板预览」子页：绿色报餐、橙色不报，切换写回个人 DSL
- 「用描述生成模板」是选择班制下的子页，不是第三种班制
- 「我的」里单独提供绑定食堂、设备与 Passkey。未登录提供邀请码注册页
- 不从员工竖屏图延伸食堂端。食堂端按 `docs/ui/` 的主参考和需求第 11 节实现
- _需求: 需求 8、需求 9、需求 14、需求 16、需求 19

- [ ] 14. 实现食堂端横屏画面
- 按需求原文第 11 节和 `docs/ui/` 实现横屏画面。导航用左侧栏主参考。强提醒用这套侧栏，不用顶栏「预警中心」。评语和改单不用旧稿的另一套导航。菜品表单只有一页：新建为空表且默认启用，编辑带出已有内容。总管页对齐数据导出、审计日志、邮箱设置、强提醒阈值、账号找回、LLM 渠道配置的参考图。SMTP 仍在配置文件。图上的示例行和未画出的渠道种类不改规则
- 缺权限码或食堂范围不覆盖时不显示画面并拒绝操作，不新增权限码
- 就餐人数只统计有效报餐，不展示暗线数值。选菜优化先给周视图，当餐选定在菜、饭、汤每一组内按偏好排序，更高更绿、更低更红。口味标签只作辅助。不出现倾向、权重、Elo。勾选立即保存，并可从早餐跳到午餐、晚餐和下一天。强提醒不自动停用菜，并按这三类分组或筛选
- 菜谱列表和菜品表单都带类别，且只能是菜、饭、汤。表单可上传一张图片并维护口味标签。列表可以显示缩略图，不强制。选菜和评分汇总显示图片，无图用中性占位。三类分组或筛选，不混成一张列表
- 食堂在自己的范围内可看匿名评语和评分汇总；匿名不展示账号，评语不提供删除
- 邀请码只在「邀请码展示」状态完整出现一次
- 导出与审计只有总管理。邮箱设置和账号找回也只有总管理，且各自独立成页
- _需求: 需求 2、需求 5、需求 10、需求 11、需求 12、需求 13、需求 14、需求 18、需求 20

- [ ] 15. 做一期验收测试
- 用 Rust 集成测试覆盖注册、会话、页内允许 / 拒绝、覆盖规则、锁定、食堂范围越权、评分窗口、匿名评语、强提醒不自动下架、渠道顺序和推送预留。菜谱缺少类别或类别不是菜、饭、汤时拒绝。非法图片或超限图片拒绝，不上传仍可保存。菜谱、选菜、评分和评语的响应不把三类混成一张列表。周视图按周一至周日返回，且每餐分组。选菜勾选离开后仍在，跳转顺序为早餐、午餐、晚餐、下一天早餐，周日晚餐的下一餐是下周一早餐。无权限取图被拒绝
- 用 Vue 测试覆盖登录顺序、确认层上的 UA 与 IP、员工端无排行、员工评分页三类分开并显示图片、班制页无上五休二、选菜周视图每格分列三类和图片且无内部术语，以及勾选后可跳到下一餐
- 在 Chrome 与 Edge 上走通注册、登录、新设备确认、报餐、截止后拒绝改单、评分和食堂强提醒
- 横屏按权限显隐：食堂看不到邀请码、截止后改单、邮箱设置、强提醒阈值、账号找回、导出和审计；食堂在范围内看得到评语和评分汇总
- _需求: 需求 1、需求 2、需求 4、需求 5、需求 9、需求 10、需求 12、需求 13、需求 14、需求 16、需求 17、需求 19、需求 20
